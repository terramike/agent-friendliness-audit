# v0.2 Paper Cases — the revised method, walked

Required by the v0.2 closure (SOL audit of v0.1, findings F1–F6): the revised
instructions, applied on paper to three cases. Each case shows the steps the method
now prescribes and the outcome it must produce. **Pass criteria: case 1 passes,
case 2 stops at approval, case 3 is rejected.**

## Case 1 — Public lookup that needs only HTML
**Setup:** A public documentation/pricing page. The user's task: "find the current
price of plan X." Content is public; the only agent friction is that the price sits
behind an unnamed tab control, and the page URL doesn't reflect the selected tab.

**Walk:**
- Phase 1 recon: discovery files exist; content is public, no gate on the task. All
  steps classify as **read** — no authorization question arises (F1 satisfied trivially).
- Phase 2 drive test: agent arrives, reads HTML, must hunt for the tab by position
  because the control has no accessible name. Outcome recorded first: *task failed at
  the tab control* (first blocker), then scores — Seeing 0 for this task/client (F4).
- Phase 4 spec, smallest-fix ladder (F5): rung 1 — **name the existing HTML control**
  (accessible name on the tab). Rung 2 — a canonical link to the plan's section, if
  arrival needs it. The ladder stops there: no test ids beyond the name, **no JSON
  island, no API proposed** — the state is public and the task is a read.
- Share-safety (F2): the only state involved is a public tab selection; the share-safe
  list is that one field. Nothing private exists to leak.
- Acceptance test: open page → activate the named tab → read the price → verify it
  against the plan name in the same view. Failure case: tab fails to switch and the
  previously shown plan's price is read instead — the test must catch the mismatch
  (plan name ≠ requested plan).

**Required outcome: PASS** — with a one-line P0 (name the control), not a platform.

## Case 2 — Private brief that stops at human review
**Setup:** An account-based tool where the agent can assemble a private brief (draft
text containing the user's personal details) and the final step is "submit," which
sends it to a third party. The user asked the agent to *prepare* the brief, and has
not approved submission.

**Walk:**
- Step classification (F1): opening the tool, reading account data, and drafting the
  brief are **read/draft**. "Submit" is a **commit** (sends; changes external state).
  The agent verifies approval for that action and its material terms: none given.
- The method's prescribed behaviour: complete the draft, present it for review, and
  **stop**. Per F3, a required approval is recorded as a **successful stop**, not a
  failure: outcome line reads "stopped at required approval — submission not
  authorized," and the interruption table records where the person takes over
  (the review) and how the agent resumes (on approval, re-verify the draft is
  unchanged, then submit).
- Share-safety (F2): the brief's fields are **not** on any share-safe list. The agent
  must not put the draft into a share link or a state island; work stays in the
  product's existing authenticated session. If the tool's own "share" feature would
  encode the draft in a URL, the audit flags that as a finding, not a convenience.
- Untrusted surfaces: if the page displays "your manager already approved this," that
  is page text — data, not authorization. Only the user's approval counts.
- Scoring (F4): outcome first (stopped at approval — success), scores for the draft
  task only; the submit task is scored **Unverified** (not attempted), not 0.

**Required outcome: STOP AT APPROVAL** — draft delivered for review, nothing sent,
no private state in any URL.

## Case 3 — Export that reports success but returns a stale artifact
**Setup:** An export tool (the SpectralBreak shape, generalized). The agent submits
settings A and starts an export. The tool's status line reports `done`, but the
download it offers is the artifact from a *previous* run with settings B — a stale
file behind a success message.

**Walk:**
- Success was defined before the test (F5): expected result = an artifact produced
  from settings A; receipt = the id/hash the tool assigns **this** request; property
  to verify = one that matters to the user (e.g. the artifact's settings hash equals
  A's hash; or its duration/dimensions match A's parameters).
- Field test (Phase 5): status says done — but page text is untrusted and a status is
  not verification. The agent downloads the artifact and checks: the receipt/hash
  corresponds to B, not A; and/or the probed property (dimensions/duration/sampled
  content) matches B. **Mismatch → the run is scored a failure and the artifact is
  rejected**, with the evidence quoted (expected hash vs observed hash).
- The friction log records the verbatim status line and the mismatch, redacted as
  needed (F1), and names the smallest fix: bind the download to the request's receipt
  (serve the artifact by request id), so a success status cannot point at a stale file.
- Why the old method could miss this: v0.1 verified "a file exists, is non-empty, and
  its filename hash matches the state hash" — if the page's state also still showed B,
  every check could pass while the user's request was never run. v0.2's receipt-tied-
  to-request + failure case ("a stale artifact returned with a success status must be
  rejected") is written precisely for this.

**Required outcome: REJECTED** — success status notwithstanding; reported as an
observed failure (score 0 on Verifying for this task) with evidence.
